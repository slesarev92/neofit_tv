# v2: Гибридный плеер ExoPlayer

## Цель

Устранить микро-лаги видео на Android-приставке H96Max (Allwinner H616, 2GB RAM).

**Корневая причина:** WebView использует SurfaceTexture для видео — каждый декодированный кадр копируется в GL-текстуру для композитинга. На H616 с shared memory bus это даёт ~180 МБ/с лишней нагрузки. Все профессиональные signage-решения (Screenly, PiSignage, Xibo, Yodeck) используют нативный ExoPlayer для видео.

**Решение:** ExoPlayer + SurfaceView (zero-copy через hardware overlay) + SimpleCache (офлайн с диска, без blob URL и RAM-аллокаций).

## Архитектура

```
MainActivity
  ├── PlayerView (SurfaceView) — видео через ExoPlayer, GONE когда изображение
  ├── WebView — изображения, poll API, расписание, placeholder
  │     └── player.js ←→ @JavascriptInterface "NativePlayer"
  ├── loadingOverlay — при загрузке страницы
  └── errorOverlay — при ошибке сети

VideoPlayerManager.kt — ExoPlayer + SimpleCache + JavascriptInterface
  - playVideo(url) → показать PlayerView, запустить ExoPlayer
  - stopVideo() → скрыть PlayerView
  - preloadVideo(url) → CacheWriter фоновая загрузка на диск
  - setCacheLimit(mb) → LeastRecentlyUsedCacheEvictor
  - Callbacks → webView.evaluateJavascript("onExoVideoEnded()" / "onExoVideoError(url)")

player.js — гибридный режим:
  - hasNativePlayer = true → playVideoNative() через NativePlayer.*
  - hasNativePlayer = false → playVideoWebView() через <video> (ПК-отладка)
  - Вся остальная логика (poll, images, schedule, watchdog) — без изменений

sw.js — кэширует только изображения (видео фильтруется в player.js)
```

## Ключевые решения (почему так)

**ExoPlayer + SurfaceView вместо WebView `<video>`:**
SurfaceView использует hardware overlay — декодированные кадры идут от VPU напрямую на дисплей без GPU-копирования. CPU ~10-15% vs ~35-40% в WebView.

**SimpleCache вместо SW Cache API для видео:**
ExoPlayer CacheDataSource читает с диска через memory-mapped I/O — без blob URL, без resp.blob(), без GC-давления. LeastRecentlyUsedCacheEvictor автоматически удаляет старые файлы при превышении лимита.

**CacheWriter для preload вместо второго `<video>`:**
CacheWriter пишет байты на диск без запуска MediaCodec — один аппаратный декодер на устройстве не конкурирует с preload. На H616 может быть только один HW decoder instance.

**LAYER_TYPE_NONE вместо LAYER_TYPE_HARDWARE:**
LAYER_TYPE_HARDWARE создаёт GPU FBO-текстуру, которая перерисовывается каждый кадр (содержимое WebView меняется). Лишняя GPU-копия без пользы.

**Обратная совместимость:**
`hasNativePlayer` проверяет `window.NativePlayer` в runtime. На ПК в браузере — fallback на текущую `<video>` логику. Серверный код не меняется.

## Офлайн-логика

**Видео (ExoPlayer SimpleCache):**
- При воспроизведении: CacheDataSource сначала проверяет диск, потом сеть
- preloadVideo() через CacheWriter фоново качает следующее видео на диск
- Без сети + файл в кэше → играет с диска (zero network)
- Без сети + файл НЕ в кэше → onExoVideoError → itemErrorCount++ → skip

**Изображения (SW Cache API):**
- Как раньше: cache-first в sw.js, precache по PRECACHE-сообщению от player.js
- player.js фильтрует видео-URL из PRECACHE когда hasNativePlayer = true

**Первый запуск без сети:**
- poll() fail → placeholder "Ошибка загрузки" → retry через pollInterval
- Плеер не дойдёт до playVideo() — нет плейлиста

**Сеть пропала после poll но до кэширования:**
- Видео: ошибки → itemErrorCount → skip после 3 попыток
- Все элементы ошибочные → 10 сек пауза → retry (защита от busy-loop)
- showLastOnError=true → последний показанный контент остаётся на экране
