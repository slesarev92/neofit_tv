## Notes (наблюдения, не обязательно к фиксу)

### `server.js:60` — `trust proxy: 1`
Корректно для одного nginx перед Node. Если когда-нибудь окажется CloudFlare/CDN перед nginx, `req.ip` начнёт врать. Сейчас ок.

### `server.js:62-78` — CSP с `'unsafe-inline'` в scriptSrc/styleSrc
Не критично без явных XSS, но при наличии бюджета на рефакторинг — вынести inline-обработчики из шаблонов и удалить `'unsafe-inline'`.

### `ecosystem.config.js:9` — `watch: false`
На проде это правильно. Просто заметить, что после изменения кода нужен `pm2 restart signage`.

### `src/modules/screens/screens.monitor.js` — `isRunning` флаг
Защита от параллельных проверок. Если одна проверка зависнет навсегда, следующие пропускаются молча. Стоит добавить таймаут с принудительным сбросом.

### `src/modules/media/media.routes.js:10` — multer пишет в `os.tmpdir()`
А потом файл перемещается в `uploads/`. На Windows это может быть медленно (разные диски / разные FS). Рассмотреть запись сразу в `uploads/_tmp/`.

### `src/modules/media/media.processor.js` — hardcoded `crf 23, preset medium`
Эти параметры — итог расследования лагов на H616 (`docs/archive/lagi.md`), менять без оснований нельзя. Но если когда-нибудь появится другой класс приставок — параметризовать через settings.

### `src/modules/pair/pair.service.js:23-32` — теоретическая гонка на генерации кода
Между `findAll()` и `create()` теоретически возможна коллизия. На 33⁶ ≈ 1.3 млрд кодов вероятность близка к нулю. Если когда-нибудь UNIQUE-constraint на код станет важен — обернуть в lock или сделать insert с retry на дубликат.

### `src/modules/settings/settings.service.js:6-14` — `copyFileAtomic` при одновременных аплоадах логотипа
`fs.rename` атомарный, tmpPath уникальный (pid + timestamp), коллизий нет. Worst case при гипотетическом одновременном аплоаде двумя админами: содержимое = последний пришедший. Текущее single-admin-окружение исключает реальный сценарий, но если когда-нибудь появится много админов — добавить очередь записи для логотипа.

### `src/modules/backup/backup.service.js:132-145` — `spawnSync('tar', …)`
На prod-Linux работает штатно. В Windows dev `tar` есть с Win10 1803+ (bsdtar в System32), но в окружениях без него (старая Win, без Git-Bash/WSL) восстановление из архива упадёт. Не блокирует регулярную работу — только функцию restore.

## False alarms (для истории — повторно не искать)

### `src/middleware/errorHandler.js:4` — `err.stack` в логах
Помечалось как утечка стектрейса. **Не баг:** это серверный лог через Winston, наружу клиенту идёт generic «Внутренняя ошибка сервера» (строка 23). Стектрейсы для оператора — нормально.

### `server.js:85` — `'dev-fallback-secret'` для сессии
Помечалось как критичное. **Не баг:** на `server.js:53-58` есть `process.exit(1)` если `SESSION_SECRET` не задан в production. В dev fallback допустим.

### `scripts/reset-password.js:21-22` — `console.log`
Помечалось как мусор. **Не баг:** это CLI-скрипт, `console.log` — это нормальный stdout для оператора.

### `src/utils/telegram.js:36` — token в URL пути
Помечалось как утечка через nginx-логи. **Не баг:** Telegram API спроектирован так. Outbound HTTPS-запросы от nginx наружу по дефолту не логируются.

### `src/modules/auth/auth.routes.js:18-21` — `pendingAuth` не чистится при неверном пароле
Помечалось как «состояние сессии может залипнуть». **Не баг:** `pendingAuth = true` устанавливается только после верного пароля. Если он уже стоит — значит пользователь раньше прошёл шаг пароля. Wrong-password attempt не добавляет attacker'у ничего, чего бы он уже не имел через скомпрометированную сессию. Чистить тут не нужно.

### `src/modules/media/media.service.js:117-124` — orphan-записи при удалении медиа во время обработки
Помечалось как риск рассинхрона. **Не баг:** `remove()` проверяет `status === 'processing'` и возвращает 409 «Файл обрабатывается, подождите завершения». Удалить медиа во время processing через API невозможно.

### Расхождения фронт ↔ API в admin SPA
Помечалось как возможный источник «иногда работает, иногда нет». **Не баг (2026-05-14):** пройдено систематически.
- Все 36 эндпоинтов из 9 `*.routes.js` имеют вызывающих в `public/`.
- Все пути и HTTP-методы совпадают (нет 404-рисков).
- Тела запросов и имена полей совпадают: `screens` `{name, playlistId}`, `playlists` `{name, items}`, `pair/confirm` `{screenId}` / `{newScreenName}`, `/api/player/:screenId/metrics` (все 8 полей: `droppedFrames, totalFrames, dropPercent, blobTimeMs, canplayTimeMs, fromCache, fileSizeKb, videoUrl`).
- Конверты ответов однообразны: списки → `{items}`, single → `{item}`, action → `{ok:true}` или `{error}`.
- `POST /api/pair/init` не имеет вызова из веб-фронта — это намеренно, эндпоинт зовётся со стороны Android-приложения (`BindingActivity.kt`).

### `src/modules/screens/screens.repository.js:57-72` — гонка в `updateLastSeen`
Помечалось как «два heartbeat могут потерять данные». При ближайшем рассмотрении **не баг:**
- `readAll()` возвращает ссылку на in-memory `cache`, оба вызывающих мутируют один объект.
- `JSON.stringify` синхронный — снимок согласован в момент записи.
- Throttle `lastFlushAt.set(id, now)` ставится **до** `await writeAll(items)` — это явная защита от двойного flush для одного screenId (комментарий в коде).
- Конкурентные flush для разных screenId сериализуют один и тот же общий `items` — никакой потери данных.

Worst case в практике: 30-секундная задержка flush; следующий heartbeat закроет хвост.
