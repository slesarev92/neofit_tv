# v2: Гибридный плеер ExoPlayer + Smart Video Processing

## Цель

Устранить микро-лаги видео на Android-приставке H96Max (Allwinner H616, 2GB RAM).

**Корневая причина:** WebView использует SurfaceTexture для видео — каждый декодированный кадр копируется в GL-текстуру для композитинга. На H616 с shared memory bus это даёт ~180 МБ/с лишней нагрузки. Все профессиональные signage-решения (Screenly, PiSignage, Xibo, Yodeck) используют нативный ExoPlayer для видео.

**Решение:** ExoPlayer + SurfaceView (zero-copy через hardware overlay) + SimpleCache (офлайн с диска, без blob URL и RAM-аллокаций).

## Архитектура

```
MainActivity
  ├── PlayerView (SurfaceView) — видео через ExoPlayer, GONE когда изображение
  ├── WebView — изображения, poll API, расписание, placeholder
  │     └── player.js ←→ @JavascriptInterface "NativePlayer"
  ├── loadingOverlay — при загрузке страницы
  └── errorOverlay — при ошибке сети

VideoPlayerManager.kt — ExoPlayer + SimpleCache + JavascriptInterface
  - playVideo(url) → показать PlayerView, запустить ExoPlayer
  - stopVideo() → скрыть PlayerView (только при переходе к картинке или ошибке)
  - preloadVideo(url) → отключён (I/O конкуренция на H616)
  - Callbacks → webView.evaluateJavascript("onExoVideoEnded()" / "onExoVideoError(url)")
  - hidePlayer() НЕ вызывается в STATE_ENDED — последний кадр остаётся

player.js — гибридный режим:
  - hasNativePlayer = true → playVideoNative() через NativePlayer.*
  - hasNativePlayer = false → playVideoWebView() через <video> (ПК-отладка)
  - NativePlayer.stopVideo() вызывается в img.onload (не раньше)
  - Вся остальная логика (poll, images, schedule, watchdog) — без изменений

sw.js — кэширует только изображения (видео фильтруется в player.js)
```

## Ключевые решения (почему так)

**ExoPlayer + SurfaceView вместо WebView `<video>`:**
SurfaceView использует hardware overlay — декодированные кадры идут от VPU напрямую на дисплей без GPU-копирования. CPU ~10-15% vs ~35-40% в WebView.

**SimpleCache вместо SW Cache API для видео:**
ExoPlayer CacheDataSource читает с диска — без blob URL, без resp.blob(), без GC-давления. LeastRecentlyUsedCacheEvictor автоматически удаляет старые файлы при превышении лимита (2GB).

**preloadVideo() отключён:**
На H616 CacheWriter конкурировал за I/O с воспроизведением (eMMC узкое горло). SimpleCache накапливает видео автоматически при воспроизведении — после 1-2 циклов плейлиста всё на диске.

**hidePlayer() только в stopVideo/onPlayerError:**
При видео→видео PlayerView остаётся VISIBLE, keep_content_on_player_reset=true держит последний кадр. Gap ~300-500мс — аппаратное ограничение H616 (MediaCodec init), принято.

**NativePlayer.stopVideo() в img.onload:**
При видео→картинка: картинка загружается под PlayerView, stopVideo вызывается только после img.onload — картинка уже видна в WebView.

**Smart video processing (remux vs transcode):**
ffprobe проверяет совместимость. Совместимое видео (h264, ≤1080p, ≤30fps, ≤8Mbps) → remux за секунды. Несовместимое → полный transcode (минуты). Экономит ~90% времени для подготовленного контента.

**SIGTERM вместо SIGKILL:**
ffmpeg корректно обрабатывает SIGTERM — завершает запись и выходит. SIGKILL убивает мгновенно но fluent-ffmpeg может не отловить ошибку.

## Офлайн-логика

**Видео (ExoPlayer SimpleCache):**
- При воспроизведении: CacheDataSource сначала проверяет диск, потом сеть
- Без сети + файл в кэше → играет с диска (zero network)
- Без сети + файл НЕ в кэше → onExoVideoError → itemErrorCount++ → skip
- Все элементы ошибочные → 10 сек пауза → retry (защита от busy-loop)

**Изображения (SW Cache API):**
- cache-first в sw.js, precache по PRECACHE-сообщению от player.js
- player.js фильтрует видео-URL из PRECACHE когда hasNativePlayer = true

## Известные ограничения

- **Gap 300-500мс при видео→видео** — аппаратное (MediaCodec init на H616). Решение через ExoPlayer playlist потребует архитектурных изменений
- **SurfaceView z-order** — SurfaceView не поддерживает alpha/bringToFront стандартным способом. Переход видео↔картинка через VISIBLE/GONE PlayerView
- **ffmpeg progress** — percent может быть null если ffprobe не определил длительность. UI показывает спиннер без процентов в этом случае
